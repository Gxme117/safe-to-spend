# Money tracker: notes for Claude Code

## What this is
A personal finance app whose first job is answering **"what can I spend today?"**.
Solo user (UK, Monzo), designed so a partner can be added later.

## How to think about the work: the Pareto principle
Before building anything, ask: what 20% of the effort gets 80% of the result?
- Pick the version of a feature that delivers most of its value for the least work, ship that, and only go further if it's clearly worth it.
- When suggesting or planning work, lead with the highest-leverage option and say what's being left out and why.
- Don't polish edge cases or build for hypotheticals before the core loop ("what can I spend today?") is solid.

## How it runs
- Published as a Claude artifact: one self-contained HTML file built from `src/` by `npm run build`.
- Runtime APIs come from the artifact host, not the browser:
  - `window.claude` database: per-user data under `data/users/me` (`state` doc, plus `tx-YYYY-MM` docs per month).
  - `mcp` host connector `host:monzo` (only in the Claude desktop app): `monzo_get_balance`, `monzo_list_pots`, `monzo_list_transactions`.
- No network requests to other sites, no remote images. Fonts: Google Fonts only.

## The money model
- Groups: **Bills** (fixed, dated), **Savings** (pots with role `save`), **Everyday** (monthly amount the user chooses), **Free** (the rest).
- Daily number = (spending money - unpaid bills before payday - what's left of everyday amounts) / days to payday.
- Spending money = main account + pots with role `spend`. Savings/business pots are never spending money.
- When there isn't enough: bills, then everyday get what's there, and the daily number is £0, never below (Safe to Spend in the mobile app too, today and days to come). The line under it says how deep the gap is, calmly ("You need £X more to cover your bills and everyday"). Never ask the user to move money in or say "short": only count what's in the account, and money coming in covers it by itself.
- Never count money that hasn't arrived. Ask instead of guessing (e.g. unsorted payments).
- Never scold. Spending big one day just lowers later days; no "overspending" language.

## Design rules
- Font: Manrope. Spacing on a 4pt grid (`--s1`..`--s7` = 4/8/12/16/24/32/48).
- Accent colour (`--btn-bg` / `--btn-ink`) means "money that's yours to use or coming in". Use it sparingly.
- Every number says why in one plain sentence. Notes under the big number stay on one line.
- Light and dark mode both matter. Respect `prefers-reduced-motion`.
- Don't recreate other companies' logos, card designs or brand colours.

## Workflow
Edit `src/`, run `npm run build`, check `dist/money-tracker.html`, commit.
Publishing to the live link is done from the Claude chat.
Work in milestones: each ends in something you can try on the phone. Finish each step in it well (tests, typecheck, lint green) before the next, and get the milestone confirmed before starting the next one.

## Mobile app (`mobile/`)
An Expo (SDK 57) + React Native + TypeScript version of the core loop. It lives beside the web app; the web app stays the live one.
The money model and design rules above apply to both. For Expo itself, follow `mobile/AGENTS.md`: check the versioned docs, install with `npx expo install`.
- `src/lib/`: the money engine, pure TypeScript ported from `src/app.js`. Every function takes `{state, txs, today}`, never globals. Keep its results matching the web app's.
- `src/db/`: payments in SQLite (`tx` table, amounts in whole pence, migrations via `PRAGMA user_version`). Pence to pounds happens only in `db/transactions.ts`.
- `src/store/`: Zustand. The settings doc (same shape as the web `state` doc) persists through `expo-sqlite/kv-store`. Payments are written to SQLite before the store updates.
- `src/app/`: routes only (Expo Router). Tests never go in here, or they become routes.
- Blur: React Native's `filter: blur()` is behind an off-by-default flag on iOS, so it does nothing here. For a CSS `blur(Npx)`, draw the text with `react-native-svg` through `<FeGaussianBlur stdDeviation={N}>` (see `SoftAmount` in `components/Hero.tsx`). Don't fake it with stacked copies.
- Glass: the Safe to Spend card can be Liquid Glass (`expo-glass-effect`, `cardStyle` in the store, Settings > Appearance), its text in the theme's ink. The choice only shows on iOS 26 (`theme/glass.ts`); anywhere else, or on Colour (the default), it's the accent card. Never set `opacity: 0` on it or anything around it (the glass stops drawing), so the wallet moves cards, it doesn't fade them.
- Taps on text controls (like the balance eye) don't dim; only the thing that changes animates. The eye works on a bank card tucked behind too, without bringing it forward. Keep show/hide fades short (about .1s): a crossfade reads slower than the web's growing blur.
- Monzo (balance, pots and payments): a personal Monzo developer client, no server. Client ID/secret and tokens live in the Keychain (`expo-secure-store`, `src/services/monzo.ts`), never in the repo or app state. Login: Safari, then paste the `https://localhost/monzo?code=…` address back (Expo Go can't catch a fixed redirect, and Monzo's login refuses an `exp://` one). Approval in the Monzo app is noticed by itself. Start over keeps the login (it's in the Keychain): setup reads from it straight away; only Disconnect removes it. A sync re-anchors `balance` to main account + `spend` pots. New pots start as `spend`: setup shows the total of everything first (it can be connected from the first setup question), and you set savings pots aside after. Connected from setup (on the first question, or on "Want us to do the boring part?" just before the bills), it reads about 3 months of payments once (Monzo shares 90 days after the first 5 minutes) and suggests from them (`src/lib/found.ts`, all pure): pay (`findPays`: payers who repeat, pay-sized payments only, the most first; else the biggest `income` in 35 days and any about its size; none, no guess), payday (the pay rule that best fits: every payday it expects has a pay within 3 days, and it explains all pays but one; the reason says "around" when it isn't exact), regular payments (`findBills`: the same payee at least twice on a rule that fits, still going; direct debits at any amount, card payments and transfers only when about the same each month or 4 weeks; food and drink and weekly card spending never) and everyday spending (`findSpending`: card payments by Monzo category a month, refunds off, found bills left out). Found isn't confirmed: nothing is saved until you've seen it. Pay is asked, not assumed ("Yes, that's right", "Choose another", "I'll enter it myself"); confirmed, it's what lands each payday and the income keeps `payer`, so a synced pay from them counts as payday. Nothing found: the page is as before. Another bank provider would plug in by returning the same `SetupFound` to `setSetupBank`. New payments are imported too, and the Day tab syncs quietly on open if the last sync is over 15 minutes old. Payments keep the shop logo Monzo sends (an https link, loaded from Monzo's servers; the web app's no-remote-images rule still stands). No logo: a line icon for what it probably was, on a soft colour (`lib/looks.ts` picks it, `components/LookIcon.tsx` draws it: by category, else guessed from the name; bills by name; pay and money in their own; colours `badgeTint` in `theme/tokens.ts`). Pure logic is in `src/lib/monzo.ts`.
- Tap any payment to say what it was (`app/payment/[id].tsx`, logic in `src/lib/payments.ts`). Money in isn't always income: it's pay (marks that payday arrived), own money moved, a refund or being paid back (`refundOf`: comes off that category's spending, never below 0), or other income. All of it stays `type: "income"`, so the balance never changes when it's re-filed. Unmatched Monzo credits stay "Money in" (`monzo-in`) until you sort them.
- Setup (`app/setup.tsx`): eight pages, balance, pay, payday, fixed bills (tap the ones you pay, `Picks` chips; "+ Add more" names your own on its own page), then "Your bills": a `Row` per pick and the monthly total (`billMonthly`, so £720 a year counts £60). Tap a row for a native page sheet (`components/BillSheet.tsx`): amount (the number pad opens), frequency, payment date. Edits apply as you make them. Nothing is required: with an amount, the first Done without a date opens the date picker, with a quiet "I'll add this later"; with no amount (blank or 0) Done just closes. A bill saved without an amount holds nothing back and says "No amount yet" on the Month tab until it's filled in there. Subscriptions gets its own sheet (`SubscriptionsSheet`): tap the ones you have, each at its usual UK monthly price (`SUBSCRIPTIONS` in `lib/bills.ts`, checked October 2026, names only; update the prices now and then), or add your own. Their total is one monthly Subscriptions bill with no payment date, since they go out on different days. The breakdown isn't kept after setup. A bill with no payment date (`billDated`) is never guessed onto a day: it holds back a month's share each pay cycle until a payment for it lands, and stays off the calendar. Then everyday spending (`lib/everyday.ts`): what you spend on (`Picks` from `EVERYDAY`, "+ Add more", "Skip for now"); "What do you normally spend?", a `Row` each, tap for `SpendSheet`: how much (an estimate is fine) and how often, the amount being each time, so one list covers "£60 every week" and "£15, 2–3 times a week" (no dates); then "Set your limits": each budget starts at what you usually spend a month (rounded, never lowered for you), editable in place, with the total and a week's worth. The end saves bills and everyday together: a pick with a budget becomes an everyday category (`budget` monthly, `usual` keeps the estimate), one without is free; usual ones keep the app's ids (`groceries`, `personal`) so Monzo payments land in them. With a bank, the bills page opens on what it found ("We found some regular payments": each on its sheet, with Remove; "+ Add a bill" for the usual list; "Pick from your payments", also on the usual list's page, lists everyone paid in those 3 months (`findPayees`), paid more than once first, to tick the ones that are bills), everyday opens on "Here's what we found" (a week's worth each, an estimate), limits are as before, and setup ends with "We've done the boring part.": the two monthly totals, tap one to go back to it. Found bills keep `source: "bank"`, `payee` and `method`; found estimates keep `usual.source: "bank"` (no `source`: typed). Savings in setup is parked for now (see `git stash list`). Setup is dark for now whatever the theme setting (`FixedTheme` in `theme/useTheme.ts`); the rest of the app follows the setting.
- Day tab: which day you're on is `lib/pager.ts` (a reducer: absolute dates, each day's pane stays on its page so landing never re-lines anything up, only the latest slide lands, a new day starts back on today). The main card only says Spent (a past day) or Safe to Spend (today, or forecast for a day to come by `forecast` in `lib/calc.ts`: spending each day's amount, expected money and pay counted from their day, each payday setting aside that cycle's bills and everyday); what's going out or coming in is in the cards below. What a day shows is `dayView` in `lib/day.ts`, all of it for that date (Everyday as of the end of it; the week's dots come from the same rows the day lists). Under the week strip (only on the week with today in it), `weekLeft` says what you could spend from now to Sunday: what today has left plus each later day's Safe to Spend, stopping the day before payday so pay that hasn't arrived isn't counted. The screen draws from those two and works nothing out itself. Under the wallet, one muted line says why the card shows what it does (the card's `reason`). Tap today's card for "Today's number" (`app/today.tsx`): "What if I spend…" (`whatIf` in `lib/today.ts`: the real engine run with that payment added, so it's always what the Day tab would then show) and where the number comes from (`todayBreakdown`). Today's Coming up is one card: today's rows, then bills, money expected and pay to payday, the first 4 (the rest on the Month tab). The pay check is one tap when it's the usual amount ("Yes, £1,800 arrived"); "A different amount" opens the field. An everyday amount says what's been spent of it ("£230 of £200"), the same under it or past it: never "over", nor "extra" (it reads as money to spend). Day 2 (`app/(tabs)/day2.tsx`, being tried out beside it) has no wallet: just the tops of the bank cards peek out above its runway of days (`CardHeads` in `components/Hero.tsx`, the wallet's offsets, the rest clipped under the runway). Tap one (not its eye) and they all come out in front, that one in full, the runway at the back; tap another to swap it to the front, as on the wallet (the stack grows to fit the card). Tap the runway to tuck them away.
- Living tab (`app/(tabs)/living.tsx`, spec and reference in `mobile/design/`): your cost of living as a ball pit, in Today's look and header styles: the number, the same labels under it (`components/FigureLabels.tsx`, shared with Today; the month stepper where Today has the day), one reason line as tall as Today's (this month's "to pay before payday" figure in ink), then 32pt to the pit or list. Each bill (at `billMonthly`; no amount, no bubble) and everyday budget is a bubble, area in step with its monthly cost (44 to 219pt), packed to the floor biggest first (`lib/living.ts`, `pack` matches the reference's to 0.1pt), paid ones last so they float on top (`pileOrder`). The bubbles are soft bodies (`lib/pit.ts`, run by `components/PitSim.tsx` only while something moves): they drop in biggest first, a drag (past 8pt; a shorter press is a tap; not while a sheet's open) shoves the others with real collisions, never passing in front, and on letting go everything drifts home like soda bubbles, the lighter of two slipping up and over; one stuck away from home slips through to it. A new or moved place is reached the same way. Reduced motion: no drop-in, a dragged bubble snaps home. Bubbles show only their icon; the amount is in the sheet. "To pay before payday" is the engine's `need`. Tap a bubble for its sheet (`components/LivingSheet.tsx`), short at first (one line: icon, name, amount), and the pile lifts onto it; tapping other bubbles only swaps the words. Swipe it up or tap it for the rest (tall); a swipe down makes it short, then closes it. Tap the bubble again, empty space or the handle to close; nothing's highlighted until a tap; the last one tapped stays highlighted, except after a tap on the bubble again or on empty space, which clears it. Its button: "Mark as paid" logs the bill's payment (amount, today, `forDate` its first unpaid due date: off the balance, no longer held back); "Mark as unpaid" removes the ones logged here, never a bank one (paid from the bank, no button); an everyday amount says "Log spending" (Add payment with it picked). Under the due line, the payments that paid it this pay cycle (`livingPayments`: filed against it, or in its category around a due date), as `TxRow`s. Edit turns the sheet into a form (name, amount, and a monthly bill's day or another's next date; an everyday amount's monthly amount), lifted above the keyboard; logic in `livingAction`, `livingPayment`, `saveLiving`. Delete (on the line with the button and Edit) removes it at once, no asking: a bill is removed (its payments stay), an everyday amount's budget goes to 0 (category and payments stay); the toast says "Rent removed · Undo" for 5s (`notify`'s `undo`), and Undo puts it back where it was. The "+" bubble opens "New bill" in the sheet, covering the pile (it doesn't lift), as in the spec's §8: name, amount, Due typed as you'd say it ("the 26th", "Saturdays", "3 March", "Fri 23 Oct": `parseDue`; blank is no payment date, except a one-off), Weekly · Monthly · Yearly · One-off with what it counts as under it (`addNote`), and the icon (picked from the name by `billLook` until you tap one; a tapped one is kept as the bill's `icon`). Add bill is grey until `addBill` makes one; the new bubble is highlighted. A One-off is a bill with `freq: "oneoff"` and a date: held back until then, and off the pile after its pay cycle. Weekly doesn't open into weekly payments yet (that's groups). The button at the top right swaps the pit for a list (`components/LivingList.tsx`, kept as `livingView` in the store): Bills in the order they're due (`livingByDue`: the next unpaid date first, one gone past at the top, then no payment date, then paid), then Everyday biggest first, each with its monthly total, a row each (its bubble, name, the sheet's due line, what it costs a month, "About" for everyday), and "Add a bill" last. A row opens the same sheet, which covers the list rather than lifting it. Bubbles and rows share `livingLabel`. An everyday amount is a fixed budget, so it's never "About". When spending keeps landing well away from it (more than 10% and £10, the same way, over or under), its sheet suggests a new one (`budgetHint` in `lib/budget.ts`, all pure): after 1 finished pay cycle if paid monthly or four-weekly, 2 fortnightly, 3 weekly (`cyclesNeeded`); only cycles the payments go back to the start of; the figure is the median, rounded (`roundBudget`); one sentence why, and what it'd do to the daily number (the real engine run with it). "Change to £X" or "Keep £Y" (`answerHint`): either sets the category's `budgetKept`, and only cycles that end after it count for the next one. Budgets are never changed without a tap. Under "Cost of living" is the calendar month on show ("Oct"; another year's "Jan 2027") with < and > either side, 12 months each way (`lib/livingMonth.ts`, all pure). This month is as above. A month gone is "Spent": each bill at what went out for it that month (filed against it, or in its category around a due date; none, no bubble), each everyday category at what was spent in it, refunds off. A month to come is "Expected": each bill at `billMonthly` (a yearly one spread, so months compare; its line says "A month's share of £180", or "£180 due …" in its month), a one-off only in its month, each everyday budget. Other months' bubbles are only to look at: no hint, and the sheet has no buttons. A month gone has no "+"; a month to come keeps it, and its New bill starts on One-off, with a day on its own ("the 3rd") falling in that month (`parseDue`'s `month`). A new month drops in afresh.
